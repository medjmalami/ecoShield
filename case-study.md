# EcoShield AI — Case Study

## Overview
EcoShield AI is a multi-service platform that performs real-time False Data Injection (FDI) attack detection and pump-power optimization for simulated smart water infrastructure. It combines a simulated sensor publisher, an Express-based streaming pipeline, two PyTorch LSTM microservices, and a Next.js dashboard into a single demo system covering two independent locations.

## Problem / Context
According to the README, the system targets two gaps that the author identifies as rarely addressed together in smart-city work: (1) energy optimization for water pumps, and (2) detection of corrupted sensor readings (FDI attacks) in real time. The README states it was built for the "AI Night Challenge" hackathon and explicitly cites academic literature on FDI attacks in smart water systems. The repo does not connect to real hardware — sensor data is generated by an in-process physics simulator (`sensorServer/src/physics.ts`) that includes demand profiles, EMA smoothing, reservoir-level tracking, and a deliberate ~8% probability of FDI attack injection for demo purposes.

## Architecture & Stack
Five independent services share data via RabbitMQ, Redis, and MongoDB. The structure under the repository root is exactly as documented in `AGENTS.md`:

- **`sensorServer/`** — Node.js + TypeScript producer. Connects to RabbitMQ (`amqplib`) and publishes 10 messages per tick (5 sensors × 2 locations) on the durable topic exchange `sensor.events`. Each message carries a fresh HS256 JWT signed with the publishing sensor's secret in the `x-token` header (`jsonwebtoken`, `expiresIn: "1m"`). Implements exponential-backoff AMQP reconnection.
- **`backend/`** — Express.js 5 + TypeScript. Consumes from queue `sensor.readings`, verifies every JWT against in-memory sensor secrets loaded from MongoDB at startup (AES-256-CBC decryption using `MASTER_KEY`), buffers readings into per-location Redis time buckets, fires the ML pipeline when 5 buckets accumulate, persists flagged anomalies to MongoDB, and broadcasts `PipelineEvent` objects to the frontend via Server-Sent Events.
- **`detectionModel/`** — FastAPI microservice exposing `POST /predict`. Loads `lstm_anomaly_early_stopping.pt` and `anomalie.pkl` from `../notebooks/`. Implements `LSTMAnomalyClassifier` (`input_dim=30, hidden_size=64, num_layers=1`) and returns `anomaly_detected: true` when the sigmoid probability ≥ 0.9. Uses the `sys.modules["__main__"]` workaround required for `torch.load` under uvicorn.
- **`optimizerModel/`** — FastAPI microservice with `LSTMRegressor2` (`input_dim=30, hidden_size=128, num_layers=2`). Loads `lstm_optimizer.pt`, the shared input scaler `anomalie.pkl`, and the output scaler `optim.pkl`. Inverse-transforms predictions back to kW.
- **`frontend/`** — Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS v4 + shadcn/ui (Radix UI primitives) + Recharts. Subscribes to SSE via `EventSource`, maintains independent rolling 30-point buffers per location, and renders a real/predicted pump-power area chart with a location toggle, alert banner, and paginated attack log.

Shared model input shape: `(5 frames × 30 floats)` = 5 sensors sorted by id ascending × 6 features `[pressure, flow_rate, temperature, pump_power, pressure_mean, pressure_var]`.

Infrastructure: `backend/docker-compose.yml` boots MongoDB 8, Redis 7 (`appendonly yes`), and RabbitMQ 3.10.5-management on a shared `ecoshield_net` bridge network.

## Notable Challenges
These are decisions with concrete evidence in the source:

- **Per-message JWT authentication at high throughput.** Every AMQP message carries a 1-minute TTL JWT in the `x-token` header, signed with that sensor's individual secret (`sensorServer/src/index.ts:108-114`). The backend verifies the signature against an in-memory `Map<sensorId, plaintextSecret>` populated at startup by decrypting AES-256-CBC ciphertexts from the `Sensor` collection using `MASTER_KEY` (`backend/src/lib/pipeline.ts:69-83`). Invalid or expired tokens are `nack`'d without requeue, and a warning is logged.
- **Per-location concurrency control.** A `pipelineRunning: Map<location, boolean>` acts as a per-location mutex; the comment explicitly notes "Node.js is single-threaded so a boolean flag is sufficient: the check+set happens synchronously before the first await" (`backend/src/lib/pipeline.ts:60-64`). The two locations run independent pipelines and do not block each other.
- **Bucket-deadline race protection.** A `sensor:closing:<location>:<bucket>` Redis String is set with `SET NX EX 30` before a bucket is assembled; whichever caller (early-arrival full-bucket path or deadline timer) wins the lock performs the assembly, the other silently exits (`backend/src/lib/pipeline.ts:147-157`).
- **Last-known-value imputation.** When the bucket deadline fires with fewer than 5 sensors, missing sensors are substituted from `sensor:last:<location>:<id>` so the `(5, 30)` model input shape is preserved. If a sensor has never reported, the entire bucket is dropped with a warning rather than zero-filled (`backend/src/lib/pipeline.ts:209-248`).
- **Shared input scaler.** Both ML services load `anomalie.pkl` and reshape `(5, 30) → (25, 6) → scaled → (1, 5, 30)`. Feature order is locked in `MODEL_FEATURES` in `backend/src/lib/pipeline.ts:40-42` and enforced on the Python side by HTTP 422 validation.
- **`torch.load` under uvicorn.** Both FastAPI services register their model class on `sys.modules["__main__"]` because the `.pt` files were pickled against `__main__` (`detectionModel/main.py:37`, `optimizerModel/main.py:36`).
- **AMQP reconnection.** Both producer (`sensorServer/src/index.ts:155-201`) and consumer (`backend/src/lib/pipeline.ts:484-523`) implement exponential backoff (`1s → 2s → … → 30s`) and null-out the channel on disconnect so the publish loop skips silently until reconnection succeeds.
- **SSE keepalive.** A 15-second `: keepalive\n\n` ping is emitted so proxies do not kill idle SSE connections; listeners and intervals are detached on client disconnect or write error (`backend/src/routes/events.ts:9-43`).
- **Schema-key rotation hygiene.** The original `seedSensors.ts` script was deleted in `9648836` because it embedded plaintext sensor keys in source; the repo's `AGENTS.md` explicitly flags this as a security regression in earlier clones.

## Outcome / Status
The repository is a working MVP/demo: Docker Compose infrastructure definition is present, both ML services load real trained models from `notebooks/`, and the README documents a full startup sequence. The optimizer README reports R² = 0.51 and MAE = 7.77 kW on training. The detection service has a hard-coded 0.9 probability threshold. There are no automated tests configured in any package — `package.json` files contain no `test` scripts, and `pytest` is not in either `requirements.txt`. The README's "Future Improvements" section lists several items still pending (historical analytics, attack classification, alerting integrations, real-sensor ingestion, online retraining, user auth, SHAP/LIME explainability, full containerization).
